为何同机要 32GB？ PostgreSQL（pgvector）+ 2 个 Celery Worker + API + Admin + Gweb + 系统预留， 在「Monitor 扫描 + 批量向量化 + 并发生成」叠加时，16GB 内存不足。

四、Worker 隔离（同机关键）

worker-content

交互型、低延迟任务

celery -A app.workers.celery_app worker \
  -Q celery,geoflow \
  --concurrency=2 \
  --loglevel=info
process_geoflow_taskLangGraph + RAG + LLM，1–5 min
evaluate_articleGEO 门禁评估
process_article_distribution含 Gweb wiki/sync

worker-batch

批处理、高吞吐、可错峰

celery -A app.workers.celery_app worker \
  -Q batch \
  --concurrency=1 \
  --loglevel=info
sync_knowledge_chunks全量 RAG 向量化
run_monitor_scan50–500 题 × 6 平台
aggregate_monitor_snapshots探针 KPI 聚合
过渡期（尚未配置 task_routes 前）：先用单 Worker --concurrency=2， 并将 Monitor 扫描与全量向量化安排在凌晨低峰，避免与内容生产叠加。

七、Nginx 与端口规划

# tech.example.com → Gweb
server {
    listen 443 ssl http2;
    server_name tech.example.com;
    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# admin.tech.example.com → GEOFlow 后台 + API
server {
    listen 443 ssl http2;
    server_name admin.tech.example.com;
    location / {
        proxy_pass http://127.0.0.1:3001;
    }
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
    }
}

十、部署验收清单

  • 全栈健康：curl https://admin.../health + Gweb 首页 200
  • Wiki 同步：GEOFlow 发布 wiki_mdx → Gweb content/wiki/ 有对应 MDX 文件
  • RAG 生产：AI_MOCK_MODE=false，上传知识库后 chunk 存在 embedding_vector
  • Monitor：手动触发 scan，探针结果写入 geo_monitor_* 表
  • 峰值压测：2 篇并发生成 + 1000 chunk 向量化，内存 < 90%、无 OOM
  • 安全：5432/6379 外网不可达；GWEB_REVALIDATE_SECRET 已轮换默认密钥
  • 网络：LLM / Embedding / 探针 API 出站稳定（大陆服务器提前验证镜像源与 API 可达性）
结论

同机承载 中等规模 GEOFlow + Gweb + 全量 RAG + AIVIS 探针， 建议采购 8 vCPU · 32 GB RAM · 200 GB NVMe · 20 Mbps 上行。 核心瓶颈是内存（PG 向量）、磁盘（向量增长）与出站网络（LLM/探针/Embedding）， 运维上必须 Worker 隔离 + 夜间批处理错峰。
